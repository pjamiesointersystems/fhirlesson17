## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

### Context
This story refactors the existing FHIR client module (`getSearchPatients.py`) to fix bugs, adopt modern library APIs, and externalize configuration. The refactored module (`fhir_client.py`) becomes the shared FHIR client for all exercise scripts in Epic 2. [Source: tech-spec.md#FR-003]

### Bugs in Current Code
Reading `getSearchPatients.py` reveals two bugs:

1. **Duplicate function definition**: `get_patient_from_server()` is defined twice (lines 13-34 and lines 69-90). The second definition shadows the first. Python allows this but it is a bug — the second definition overwrites the first. Remove the second occurrence. [Source: read of FHIRAI/getSearchPatients.py lines 13-34, 69-90]

2. **Pydantic v1 API**: All resource parsing uses `parse_obj()`, which is Pydantic v1. Pydantic v2 (required by fhir.resources 7.x) replaces this with `model_validate()`. [Source: tech-spec.md#FR-008, tech-spec.md#FR-003]

### fhir.resources 7.x R4B Import Migration
Version 7.x of fhir.resources organizes resource classes into sub-packages by FHIR version. The lesson uses FHIR R4, which in version 7.x is the `R4B` (R4 Ballot) sub-package. [Source: tech-spec.md#FR-008]

**Import changes:**
```python
# Old (6.x)
from fhir.resources.patient import Patient
from fhir.resources.observation import Observation
from fhir.resources.bundle import Bundle

# New (7.x)
from fhir.resources.R4B.patient import Patient
from fhir.resources.R4B.observation import Observation
from fhir.resources.R4B.bundle import Bundle
```

If the import path turns out to be different (e.g., `R4` instead of `R4B`), the validation test will fail with `ImportError`. Document the actual path discovered and adjust accordingly. The smoke test in Story 1.1 should have verified the correct path. [Inference; dependency on Story 1.1]

### Pydantic v2 Migration: parse_obj() → model_validate()
Pydantic v2 renames the model construction method. The signature and behavior are the same — both take a dict and return a validated model instance. [Inference based on Pydantic v2 migration guide]

**Change:**
```python
# Old (Pydantic v1)
patient = Patient.parse_obj(json_data)

# New (Pydantic v2)
patient = Patient.model_validate(json_data)
```

Apply this change in:
- `get_patient_from_server()` (line 33)
- `get_patients_from_server()` (line 66, inside list comprehension)
- `get_observations_for_patient()` (line 154, inside list comprehension)

The duplicate `get_patient_from_server()` (lines 69-90) also has this call, but that function is being removed, so no change needed there. [Source: read of FHIRAI/getSearchPatients.py]

### Configuration Externalization
All functions currently hardcode:
- Base URL: `http://127.0.0.1:8080/csp/healthshare/demo/fhir/r4`
- Credentials: `("_System", "ISCDEMO")`

Replace these with imports from `config.py`:
```python
from config import FHIR_BASE_URL, FHIR_USERNAME, FHIR_PASSWORD

# In each function:
url = f"{FHIR_BASE_URL}/Patient/{patient_id}"
response = requests.get(url, headers=headers, auth=(FHIR_USERNAME, FHIR_PASSWORD))
```

Five functions construct URLs: `get_patient_from_server()`, `get_patients_from_server()`, `search_patients_get_ids()`, `get_observations_for_patient()`, `get_everything_for_patient()`. Update all five. [Source: read of FHIRAI/getSearchPatients.py; tech-spec.md#FR-007]

### New Helper: get_resource_counts()
Exercise 2 (Story 2.2) needs to count resources by type in a bundle. This helper centralizes that logic. [Source: tech-spec.md#FR-003]

**Signature:**
```python
def get_resource_counts(bundle_dict: dict) -> dict:
    """
    Counts resources by type in a FHIR Bundle.

    Args:
        bundle_dict: A FHIR Bundle as a Python dict (from response.json())

    Returns:
        A dict mapping resource type to count, e.g.:
        {"Patient": 1, "Observation": 23, "Condition": 5}
    """
    resources = fhirpath(bundle_dict, "Bundle.entry.resource")
    counts = {}
    for res in resources:
        resource_type = res.get("resourceType", "Unknown")
        counts[resource_type] = counts.get(resource_type, 0) + 1
    return counts
```

This function is pure data processing — no FHIR server call. It operates on an already-fetched bundle dict. [Inference]

### Module vs. Script
The current `getSearchPatients.py` has an `if __name__ == "__main__":` block that runs a test. Remove this. The refactored `fhir_client.py` should be a library module, not a script. Tests belong in separate validation scripts (ephemeral, not committed). [Inference]

### Validation Strategy
Two validation tests:

1. **Integration test**: Call `get_everything_for_patient("2")` against the live IRIS FHIR server. This verifies:
   - Imports work (R4B sub-package is correct)
   - Config is read correctly (FHIR_BASE_URL, credentials)
   - `model_validate()` works (no AttributeError)
   - The function returns data as expected

2. **Helper test**: Call `get_resource_counts()` on the bundle from test #1. Verify it returns a dict with string keys and integer values.

Both tests are environmental (depend on live FHIR server) and ephemeral (not committed). The IRIS FHIR server is part of the course infrastructure and should be running during development. [Source: CLAUDE.md#fhir-server-configuration; Inference]

### Educational Context
Students will import this module in Exercises 2, 3, and 4. The module should be clean, well-commented, and exemplary — it is part of the lesson's teaching. Function docstrings should explain what each function does and what it returns. [Inference]

### Relationship to getSearchPatients.py
This story creates `fhir_client.py` as a new file. The old `getSearchPatients.py` remains in place (unmodified) for now. Story 3.4 (file cleanup) will archive it. This avoids mid-refactor confusion where the old file is half-deleted. [Source: tech-spec.md#FR-009]

### Error Handling
The existing code uses `response.raise_for_status()` to raise exceptions on HTTP errors. Keep this pattern — it is appropriate for educational code where exceptions are more instructive than complex error handling. Exercise scripts will catch exceptions and present friendly messages. [Inference]

### Validation Strategy
This story's testing is integration-level (live FHIR server) and functional (do the functions work?).

**Test 1: get_everything_for_patient() Integration**
- Environment: IRIS FHIR server running at configured URL with Synthea data loaded (patient ID "2" exists)
- Precondition: `.env` file exists with correct FHIR server settings (or defaults are correct)
- Steps:
  1. Create throwaway script `test_fhir_client.py` in `FHIRAI/`
  2. `from fhir_client import get_everything_for_patient`
  3. `resources = get_everything_for_patient("2")`
  4. `assert isinstance(resources, list)`
  5. `assert len(resources) > 0`
  6. `assert resources[0].get("resourceType") is not None`
  7. Expected: Function returns a list of resource dicts, no exceptions
- Success criteria: Assertions pass, no `ImportError`, no `AttributeError`, no HTTP error

**Test 2: get_resource_counts() Function**
- Environment: Same as Test 1
- Steps:
  1. Continue in `test_fhir_client.py`
  2. `from fhir_client import get_resource_counts`
  3. Fetch bundle dict: `import requests; from config import FHIR_BASE_URL, FHIR_USERNAME, FHIR_PASSWORD`
  4. `response = requests.get(f"{FHIR_BASE_URL}/Patient/2/$everything", auth=(FHIR_USERNAME, FHIR_PASSWORD))`
  5. `bundle_dict = response.json()`
  6. `counts = get_resource_counts(bundle_dict)`
  7. `assert isinstance(counts, dict)`
  8. `assert all(isinstance(k, str) and isinstance(v, int) for k, v in counts.items())`
  9. `assert counts.get("Patient", 0) >= 1`
  10. Expected: `counts` is a dict like `{"Patient": 1, "Observation": 23, ...}`
- Success criteria: Assertions pass, function returns expected structure

**Test 3: Pydantic v2 API Verification**
- Environment: Same as Test 1
- Steps:
  1. Continue in `test_fhir_client.py`
  2. `from fhir_client import get_patient_from_server`
  3. `patient = get_patient_from_server("2")`
  4. `assert hasattr(patient, "id")`
  5. `assert patient.id == "2"`
  6. Expected: Function returns a fhir.resources Patient object, no AttributeError from `parse_obj()`
- Success criteria: Function works, proving `model_validate()` is in use

**Test 4: No Duplicate Function**
- Steps:
  1. Open `fhir_client.py` in an editor
  2. Search for `def get_patient_from_server`
  3. Expected: Exactly one occurrence
- Success criteria: Function is defined only once

**Test 5: R4B Import Verification**
- Steps:
  1. Start Python REPL
  2. `from fhir_client import get_patient_from_server`
  3. Expected: No ImportError
- Success criteria: Module imports successfully, proving R4B sub-package path is correct

**Edge Case: FHIR Server Unreachable**
- If the FHIR server is not running, `requests.get()` will raise `requests.exceptions.ConnectionError`, and `raise_for_status()` will not be reached. This is expected behavior. Exercise scripts will catch this and present a friendly message. No special handling needed in `fhir_client.py`. [Inference]

**Edge Case: Patient ID Does Not Exist**
- If `get_patient_from_server("999999")` is called with a nonexistent ID, the FHIR server returns a 404 and `raise_for_status()` raises `requests.exceptions.HTTPError`. This is expected behavior. No special handling needed. [Inference]

**No Unit Tests for Individual Functions**
Each function is a thin wrapper around a REST call and fhirpath extraction. There is no complex logic to unit test in isolation. The integration tests (calling live FHIR server) are the appropriate validation. [Inference]
