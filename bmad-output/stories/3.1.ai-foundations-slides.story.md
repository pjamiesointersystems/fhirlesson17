## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

### Purpose

This content serves as Phase 1 of the restructured Lesson 17, providing the conceptual foundation that makes the rest of the AI+FHIR series coherent. Students entering the lesson have completed prior FHIR lessons but have no AI/ML background. [Source: SPEC.md#problem, tech-spec.md#problem-statement]

### Topics and Healthcare Analogies (from tech-spec.md#FR-001)

Each topic must include at least one healthcare analogy. Suggested analogies are provided in the tech spec:

1. **LLM architecture (conceptual)**: Explain what an LLM is without mathematics. Compare to a clinician's knowledge base built from vast training (medical school, residency, journals) but applied to new patient cases. [Inference]

2. **Tokens and tokenization**: Analogy — pharmacist reading prescriptions; each word or subword is a unit the system processes. Token boundaries don't always match word boundaries (e.g., "unresponsive" might be "un-responsive" or "unresp-onsive" to the tokenizer). [Source: tech-spec.md#FR-001]

3. **Context windows**: Analogy — clinician working memory; a physician can only hold a limited amount of chart information in mind at once. If a patient has 500 encounters, the clinician must review summaries or focus on recent data. LLMs face the same constraint. [Source: tech-spec.md#FR-001]

4. **Embeddings (brief)**: "Meaning as numbers" — words and phrases are converted to numeric vectors that capture semantic relationships (e.g., "hypertension" is closer to "high blood pressure" than to "diabetes" in embedding space). Detailed coverage of embeddings and vector similarity is deferred to the RAG Lab. [Source: tech-spec.md#FR-001, SPEC.md#non-goals]

5. **Temperature and sampling**: Analogy — confident specialist (low temperature, deterministic) vs. creative brainstormer (high temperature, diverse ideas). For clinical summarization, lower temperature is safer; for generating differential diagnoses, higher temperature might surface creative hypotheses. [Source: tech-spec.md#FR-001]

6. **Prompts and system roles**: Analogy — clinical protocols guiding behavior. A system prompt is like a hospital policy ("always verify allergies before prescribing") that shapes all subsequent interactions. User prompts are like the specific clinical question ("summarize this patient's chart"). [Source: tech-spec.md#FR-001]

7. **Hallucination**: Analogy — clinical confabulation; the LLM is confident but wrong, filling gaps with plausible-sounding but fabricated information. In healthcare, hallucination is a critical safety risk (e.g., inventing a medication the patient never took). [Source: tech-spec.md#FR-001]

8. **Local vs. cloud models**: Trade-offs: local models (privacy, HIPAA-friendly, latency) vs. cloud models (capability, cost). For PHI, local models are essential unless using a BAA-backed cloud API. Analogy — local lab vs. reference lab: local is fast and private, reference lab has more sophisticated tests. [Source: tech-spec.md#FR-001]

9. **Model selection basics**: Explain size vs. capability (3B params vs. 70B params vs. GPT-4 scale). When is a 3B local model sufficient (simple summarization, extraction) vs. when is a larger cloud model necessary (complex reasoning, differential diagnosis)? [Source: tech-spec.md#FR-001]

### Content Format

Deliverable is a markdown document or slide outline. Visual formatting (fonts, colors, transitions) is out of scope — instructor will format according to preference. Focus on textual content, section structure, and inline notes for suggested visuals (e.g., "Diagram: context window as a sliding buffer over a long patient chart"). [Source: tech-spec.md#FR-001]

### Audience and Tone

Students have FHIR knowledge (resource types, bundles, FHIRPath, FHIR servers) but no AI/ML background. Avoid jargon that requires machine learning prerequisites (e.g., "backpropagation", "attention mechanisms"). Use healthcare contexts they already understand to explain new AI concepts. [Source: SPEC.md#capabilities, tech-spec.md#FR-001]

### Series Context

This content is Phase 1 of Lesson 17, which is the first lesson in a four-part series:
1. Lesson 17 — foundations (this content + exercises)
2. Part One — agentic AI architecture, MCP, tool-use
3. Part Two — FHIR as knowledge layer, subagents, safety patterns
4. RAG Lab — vector stores, HNSW, hybrid search, Graph RAG

The content must establish concepts that the downstream lessons assume. [Source: SPEC.md#series-context, tech-spec.md#problem-statement]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

### Strategy

Content testing is primarily pedagogical review, not automated testing. The dev tool should verify:

1. **Completeness check**: Confirm all 9 required topics are present in the content file (LLM architecture, tokens, context windows, embeddings, temperature, prompts, hallucination, local vs. cloud, model selection). This is a manual checklist against tech-spec.md#FR-001.

2. **Analogy audit**: For each topic, verify at least one healthcare analogy is present and clearly connects to clinical/FHIR contexts students already know. Mark any topic missing an analogy.

3. **Scope boundary check**: Search the content for terms that signal out-of-scope depth: "agentic", "MCP", "RAG", "vector store", "tool use". Each occurrence must be a forward reference (e.g., "this is covered in Part One") rather than in-depth teaching. Flag any in-depth treatment of out-of-scope topics.

4. **Accessibility review**: Read each section and note any use of mathematical notation, ML jargon (e.g., "backpropagation", "transformer architecture"), or assumptions of prior AI knowledge. Content should be understandable by someone who has only completed the FHIR lessons.

5. **Format deliverable check**: Confirm the file is readable markdown (or equivalent plain text outline) and does NOT include visual formatting artifacts (PowerPoint, Keynote, PDF). The instructor will handle visual formatting.

No test code, no coverage metrics, no automated fixtures. This is human-reviewed content.
