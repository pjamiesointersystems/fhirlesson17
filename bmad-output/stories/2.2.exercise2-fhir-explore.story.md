## Story

**As a** healthcare informatics student learning to combine FHIR and LLMs
**I want** a script that retrieves a patient's complete FHIR record and shows concrete numbers about its size and structure
**So that** I understand why raw FHIR JSON cannot be naively sent to an LLM (context window limits) and need structured processing before summarization.

---

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Script retrieves a `Patient/$everything` bundle from the IRIS FHIR server for a configurable patient ID (default patient ID "2") and handles connection errors gracefully.
2. Script prints concrete bundle statistics: total character count, estimated token count (via tiktoken), total resource count, and resource count broken down by type (e.g., "Patient: 1, Observation: 23, Condition: 5").
3. Script demonstrates the "too big for context window" problem by comparing bundle token count to a typical context window size (e.g., 8K tokens) and printing a clear statement if bundle exceeds capacity.
4. Script uses the refactored `fhir_client.py` module (from Story 1.3) for FHIR server access; all FHIR HTTP calls go through fhir_client functions, not inline requests.
5. Script output is pedagogically clear with labeled sections: "Bundle Statistics", "Resource Breakdown", "Context Window Analysis", making the size problem concrete and visible.

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

**Purpose:** Exercise 2 bridges from Exercise 1's LLM basics to Exercise 3's FHIR+LLM integration. Students see the raw scale of a FHIR patient bundle and understand why naive "send JSON to LLM" fails. The concrete numbers (character count, token count, resource breakdown) make the context window problem tangible, motivating the structured extraction approach in Exercise 3.

**Requirements Covered:**
- FR-003: Exercise 2 — FHIR bundle retrieval and exploration [Source: tech-spec.md#FR-003]
  - Note: FR-003 also covers the fhir_client.py refactor (Story 1.3), but this story uses the refactored module; it does not implement the refactor itself.

**Implementation Guidance:**

1. **FHIR Bundle Retrieval** [Source: tech-spec.md#FR-003]
   - Use `fhir_client.get_everything_for_patient(patient_id)` from the refactored module (Story 1.3)
   - Default patient ID: "2" (matches existing fhirapp.py default and 100Set/ sample data) [Source: CLAUDE.md#running]
   - Allow command-line override: `python exercise2_fhir_explore.py --patient 5` or environment variable `PATIENT_ID=5`
   - FHIR server URL and credentials come from config.py → .env [Source: tech-spec.md#FR-007]

2. **Bundle Statistics Calculation** [Source: tech-spec.md#FR-003]
   - **Character count:** Serialize bundle to JSON string, count characters. This shows raw size.
   - **Token count estimate:** Use tiktoken with `cl100k_base` encoding (OpenAI GPT-3.5/4 tokenizer) [Source: tech-spec.md#FR-004, tech-spec.md#technology-stack]
     - **Important:** Document in code comments that this is an approximation. Local models (Llama, Mistral, etc.) use different tokenizers, so actual token count may vary by ±20%. This approximation is sufficient for demonstrating the size problem and is a teaching moment about tokenizer differences. [Source: tech-spec.md#risks-mitigations, tech-spec.md#decisions-log-summary]
   - **Total resource count:** `len(bundle_dict["entry"])` assuming standard Bundle structure
   - **Resource count by type:** Iterate `bundle_dict["entry"]`, extract `entry["resource"]["resourceType"]`, count occurrences per type. If fhir_client.py provides a `get_resource_counts(bundle_dict)` helper (from Story 1.3), use that. [Source: tech-spec.md#key-components - fhir_client.py should add this helper]

3. **Context Window Analysis** [Source: tech-spec.md#FR-003]
   - Compare bundle token count to a typical context window size: 8K tokens (representative of smaller local models and older cloud models)
   - Print whether bundle fits or exceeds
   - This demonstrates the "too big for context window" problem concretely [Source: tech-spec.md#FR-003]
   - Optional enhancement: show percentage utilization (e.g., "150% of 8K window — requires chunking or processing")

4. **Output Format** [Source: tech-spec.md#FR-003]
   - Three labeled sections: "Bundle Statistics", "Resource Breakdown", "Context Window Analysis"
   - Clear, pedagogical language. Example output:
     ```
     === Bundle Statistics ===
     Patient ID: 2
     Total characters: 45,234
     Estimated tokens: ~12,000 (using tiktoken cl100k_base approximation)
     Total resources: 47

     === Resource Breakdown ===
     Patient: 1
     Observation: 23
     Condition: 5
     MedicationRequest: 8
     Encounter: 10

     === Context Window Analysis ===
     This bundle contains ~12,000 tokens.
     A typical 8K context window holds 8,192 tokens.
     ❌ Bundle exceeds capacity by ~3,808 tokens (146% of limit).
     → Raw JSON cannot be sent to LLM without processing.
     ```

5. **Error Handling** [Source: tech-spec.md#error-handling-strategy]
   - **FHIR server unreachable:** Catch connection errors from fhir_client, print "Cannot connect to FHIR server at {url}. Is IRIS running? See Readme setup instructions."
   - **Empty bundle or patient not found:** If bundle has no entries, print "Patient {id} not found or has no resources."
   - **Malformed bundle structure:** If `bundle_dict["entry"]` is missing, handle gracefully (unlikely with real IRIS responses, but defensive coding for educational context)

6. **Tiktoken Approximation Note** [Source: tech-spec.md#FR-004, tech-spec.md#risks-mitigations]
   - Include a code comment near the tokenization call explaining:
     ```python
     # Note: tiktoken cl100k_base is an approximation. Local models (Llama, Mistral)
     # use different tokenizers. Actual token count may vary by ±20%. This is sufficient
     # for demonstrating the context window problem and is a teaching moment about
     # tokenizer differences across LLMs.
     ```
   - This addresses the risk flagged in tech-spec.md that students may notice discrepancies; turn confusion into learning

**Dependencies:**
- Story 1.3 (fhir_client.py refactor) must be complete [Source: tech-spec.md#FR-003 - Exercise 2 uses refactored module]
- Story 1.2 (config.py) must be complete [Source: tech-spec.md#FR-007 - FHIR server config]
- IRIS FHIR server running with Synthea data loaded (student setup) [Source: tech-spec.md#assumptions]

**Edge Cases:**
- Patient ID not found: print "Patient {id} not found"
- Empty bundle (patient exists but no resources): print message, don't crash
- FHIR server returns error response: catch and print HTTP status and message
- Very large bundle (>100K tokens): script should still run, but analysis will show massive excess over 8K window

**Testing Strategy:**
- Manual verification: Run with default patient "2" → should print statistics with reasonable numbers (based on Synthea data)
- Manual verification: Run with FHIR server stopped → should print connection error
- Manual verification: Run with invalid patient ID → should print "not found" message
- Code inspection: Verify tiktoken approximation comment is present
- Code inspection: Verify fhir_client functions are used (no inline requests.get())
