## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

### Purpose

This content serves as Phase 3 (partial) of the restructured Lesson 17, connecting the foundational concepts and exercises to the rest of the four-part AI+FHIR series. Students should leave Lesson 17 understanding where each concept reappears and why the series is structured as it is. [Source: SPEC.md#problem, tech-spec.md#FR-011]

### Connection Points (from tech-spec.md#FR-011)

The content must explain four key connections between Lesson 17 and the downstream lessons:

#### 1. Patient Summarization Pipeline → Subagent (AC: #1)

**Lesson 17 (Exercise 3):** A CLI pipeline that fetches a FHIR bundle, groups resources by type, extracts structured fields, sends to LLM, and prints a summary. This is a single-purpose, linear workflow.

**Part One/Two:** The same pipeline becomes a **subagent** within a multi-agent architecture. Part One teaches how agents are orchestrated via MCP and structured tool calls. Part Two shows the summarizer as one of several agents (others: terminology normalizer, differential diagnosis generator) that share a FHIR-as-knowledge-layer.

**Bridge content:** Explain that Lesson 17 teaches the "inner loop" (fetch → extract → LLM → output), and Parts One/Two teach the "outer loop" (agent coordination, tool-use, safety patterns). Students learn to build a working summarizer before learning how it fits into a larger system.

[Source: tech-spec.md#FR-011, SPEC.md#series-context]

#### 2. Structured Feature Extraction → RAG Vector Pipeline (AC: #2)

**Lesson 17 (Exercise 3):** Resource-type grouping and field extraction produce structured, clinically-relevant data (e.g., "Patient: demographics, Conditions: list of active conditions, Observations: recent lab values"). This is more useful for LLM summarization than raw JSON.

**RAG Lab:** The same structured extraction is the **input** to the RAG pipeline. The Lab teaches how to embed these structured fields, store them in a vector database (HNSW index), and retrieve them via semantic search. The structured extraction ensures that embeddings capture clinically meaningful concepts rather than JSON noise.

**Bridge content:** Explain that Lesson 17's extraction is "RAG prep" — you can't embed raw FHIR JSON effectively, so you extract first. The RAG Lab builds on this by teaching embeddings, vector stores, and hybrid search.

[Source: tech-spec.md#FR-011, SPEC.md#series-context]

#### 3. Prompt Engineering → Agent Prompts (AC: #3)

**Lesson 17 (Exercise 4):** Prompt engineering techniques — system roles ("You are a clinical assistant"), structured output instructions ("Produce a summary with sections: Demographics, Conditions, Medications"), few-shot examples.

**Part One/Two:** The same techniques apply to prompting agents. Part Two teaches how to prompt a summarizer agent within a multi-agent system, where the system prompt includes context from other agents' outputs. The principles are the same; the complexity increases.

**Bridge content:** Explain that prompt engineering is a skill students will use in every AI+FHIR application. Exercise 4 teaches the basics; Parts One/Two show how to apply them in production-like scenarios.

[Source: tech-spec.md#FR-011]

#### 4. MCP Preview (AC: #4)

**Lesson 17:** Manual FHIR server interaction via `requests`. Students explicitly call the FHIR API, parse responses, and handle errors.

**Parts One/Two:** MCP (Model Context Protocol) standardizes how LLMs connect to external systems. An MCP server exposes FHIR operations (e.g., "fetch patient", "search observations") as tools that the LLM can invoke. The LLM decides which tool to call based on the user's query; the MCP server executes the call and returns structured results.

**Bridge content:** Explain that Lesson 17 teaches "manual mode" — you write the FHIR query code yourself. Parts One/Two teach "autonomous mode" — the LLM writes the query (via tool calls) and the MCP server executes it. Students need manual-mode understanding before they can debug or extend autonomous systems.

[Source: tech-spec.md#FR-011, SPEC.md#non-goals]

### Content Scope Boundary (AC: #5)

This content is a **bridge**, not a preview lesson for Parts One/Two or RAG Lab. Do NOT:

- Teach multi-agent architecture (e.g., how agents coordinate, what an orchestrator is)
- Teach MCP server/client implementation (e.g., how to write an MCP tool, protocol details)
- Teach RAG pipelines (e.g., how to embed, how HNSW works, query strategies)
- Teach agentic AI patterns (e.g., tool-use, chain-of-thought, least privilege)

Instead, explain the **connection points**: "You learned X in Lesson 17; in Part One you'll see how X becomes part of a larger system Y." Keep each connection to 1-2 paragraphs. [Source: tech-spec.md#FR-011]

### Content Format

Deliverable is a markdown document or slide outline. Visual formatting (fonts, colors, transitions) is out of scope — instructor will format according to preference. Suggest a diagram: a visual map showing Lesson 17 concepts (summarization, extraction, prompts, FHIR access) with arrows to Parts One/Two and RAG Lab concepts (subagents, MCP, RAG, vector stores). [Inference]

### Tone and Style

Bridge content should be forward-looking and encouraging. Frame the series as a progressive journey: "You've built the foundation; now let's scale it up." Avoid language that implies Lesson 17 is simplistic or incomplete — it is foundational by design. [Inference]

### Series Context

This content is part of Phase 3 (discussion/bridge) of Lesson 17, which is the first lesson in a four-part series:
1. Lesson 17 — foundations (AI concepts, exercises, safety frame)
2. Part One — agentic AI architecture, MCP, tool-use, safety patterns
3. Part Two — FHIR as knowledge layer, subagents, safety operationalization
4. RAG Lab — vector stores, HNSW, hybrid search, Graph RAG

The bridge content must make the series structure explicit and motivate students to continue. [Source: SPEC.md#series-context, tech-spec.md#problem-statement]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

### Strategy

Content testing is primarily pedagogical review. The dev tool should verify:

1. **Completeness check**: Confirm all 4 required connection points are present in the content file (summarization → subagent, extraction → RAG, prompts → agent prompts, MCP preview). This is a manual checklist against tech-spec.md#FR-011.

2. **Connection point audit**: For each of the 4 topics, verify that the content:
   - Explains what was taught in Lesson 17
   - Explains how it reappears in Parts One/Two or RAG Lab
   - Does NOT teach the downstream topic in depth

   Mark any topic that teaches downstream content (e.g., "Here's how to write an MCP server") as out-of-scope and flag for simplification.

3. **Scope boundary check**: Search the content for terms that signal in-depth teaching of downstream topics: "orchestrator", "tool schema", "HNSW index", "embedding model". Each occurrence should be a brief mention or forward reference, not detailed instruction. Flag any in-depth treatment.

4. **Series structure verification**: Verify that the content makes the four-part series structure explicit (Lesson 17 → Part One → Part Two → RAG Lab) and explains the role of each part. If the series structure is missing or unclear, mark for addition.

5. **Tone review**: Read the content and flag any language that is overly simplistic ("In Lesson 17 you learned baby stuff") or dismissive of the foundation. Bridge content should be positive and forward-looking.

No test code, no coverage metrics, no automated fixtures. This is human-reviewed content.
