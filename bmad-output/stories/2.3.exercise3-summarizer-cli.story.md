## Story

**As a** healthcare informatics student learning AI+FHIR integration
**I want** a CLI pipeline that retrieves a patient's FHIR record, groups resources by type, extracts clinical features, and generates a structured summary via local LLM
**So that** I see a complete, working AI+FHIR application and understand how to prepare FHIR data for LLM consumption beyond naive JSON chunking.

---

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Script runs as a CLI pipeline (no GUI, no TUI) that fetches `Patient/$everything`, groups resources by type (Patient, Condition, Observation, MedicationRequest, etc.), extracts clinical features per resource type, sends structured data to LLM, and prints a clinical summary to terminal.
2. Resource grouping produces better, more coherent summaries than raw JSON chunking by organizing data semantically (all Conditions together, all Observations together, etc.) before LLM processing.
3. Script uses a structured system prompt that specifies output format (Demographics, Active Conditions, Medications, Recent Encounters, Recent Observations, Allergies, Notable Findings sections) and includes a "do not invent" instruction.
4. Script handles dynamic data volumes without hardcoded chunk limits; if a patient has 3 Conditions or 50 Observations, the pipeline adapts without code changes.
5. Script prints progress indicators to terminal (e.g., "Fetching bundle...", "Grouping 47 resources...", "Extracting features...", "Generating summary...") and final structured summary, making the pipeline stages visible to students.

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

**Purpose:** Exercise 3 is the capstone hands-on exercise — a complete AI+FHIR application that demonstrates the full pipeline from FHIR retrieval to LLM-generated clinical summary. Students see how structured feature extraction (grouping by resource type, extracting clinical fields) produces better summaries than the naive "chunk raw JSON and send to LLM" approach demonstrated as failing in Exercise 2.

**CRITICAL CONTEXT CHANGE:** Textual TUI has been DROPPED. Exercise 3 is now a CLI pipeline (fetch → group → extract → LLM → print). The instructor demos artifacts via a separate Angular front end (out of scope). This eliminates the highest-risk dependency migration (Textual 0.44 → 8.x) and keeps the lesson focused on AI+FHIR concepts rather than UI framework specifics. [Source: sharding-context.md#critical-decision, decision-log.md#drop-textual-tui]

**Requirements Covered:**
- FR-004: Exercise 3 — Patient summarization pipeline (MODIFIED to CLI, not TUI) [Source: tech-spec.md#FR-004]
  - Original FR-004 specified Textual TUI; sharding-context.md overrides this to CLI pipeline
  - Core functionality (grouping, extraction, structured prompt, LLM call) remains unchanged

**Implementation Guidance:**

1. **CLI Pipeline Structure (NOT TUI)** [Source: sharding-context.md#critical-decision]
   - This is a command-line script: `python exercise3_summarizer.py --patient 2`
   - No Textual imports, no TUI widgets, no `App` class, no `compose()` methods
   - Progress printed to terminal via simple `print()` statements
   - Final summary printed to terminal as text output
   - Students observe the pipeline stages via print statements, not a live-updating UI

2. **Phase 1: FHIR Data Retrieval** [Source: tech-spec.md#FR-004]
   - Use `fhir_client.get_everything_for_patient(patient_id)` from Story 1.3
   - Patient ID from CLI argument (`--patient` or `-p`) or default "2"
   - Error handling: if bundle retrieval fails, print error and exit gracefully

3. **Phase 2: Resource Grouping** [Source: tech-spec.md#FR-004]
   - Parse `bundle_dict["entry"]` and group resources by `resourceType`
   - Create a dictionary: `grouped = {"Patient": [], "Condition": [], "Observation": [], ...}`
   - This semantic organization is KEY to producing better summaries than raw JSON chunking [Source: tech-spec.md#decisions-log-summary - resource-type grouping rationale]
   - Print resource counts per type (like Exercise 2) so students see the data volume per type

4. **Phase 3: Clinical Feature Extraction** [Source: tech-spec.md#FR-004]
   - For each resource type, extract clinically relevant fields and format compactly
   - **Patient:** name (family, given), birthDate, gender
   - **Condition:** code.text (or code.coding[0].display), clinicalStatus.coding[0].code, onsetDateTime
   - **Observation:** code.text, valueQuantity.value + unit, effectiveDateTime (limit to recent 10-20 to avoid overwhelming LLM)
   - **MedicationRequest:** medicationCodeableConcept.text, status, dosageInstruction.text
   - **Encounter:** type.text, period.start, status (limit to recent 5-10)
   - **AllergyIntolerance:** substance.text, reaction, severity
   - Produce compact text, NOT full JSON. Example for one Condition: "Active: Type 2 Diabetes (onset 2018-03-15)"
   - This is "structured feature extraction as previewed in Part One slides" [Source: tech-spec.md#FR-004]
   - Handle missing fields gracefully (many FHIR resources have optional fields)

5. **Phase 4: LLM Summarization with Structured Prompt** [Source: tech-spec.md#FR-004]
   - **System prompt:**
     - Role: "You are a clinical AI assistant reviewing patient data."
     - Output format specification: "Summarize into sections: Demographics, Active Conditions, Medications, Recent Encounters, Recent Observations, Allergies, Notable Findings."
     - Safety instruction: "Do not invent information not present in the data. If a section has no data, state 'None recorded.'"
   - **User message:** Append the extracted features (compact text from Phase 3)
   - Call `config.get_llm_client().chat(...)` or equivalent with model from config
   - Timeout: use generous timeout (60-120s) for larger patient records and slower hardware

6. **Phase 5: Output Display** [Source: tech-spec.md#FR-004]
   - Print the LLM response to terminal with a clear header: "=== Patient Clinical Summary ==="
   - No fancy formatting — plain text is fine for CLI output
   - Optionally: save summary to a file (`patient_{id}_summary.txt`) for student review

7. **Dynamic Handling (No Hardcoded Limits)** [Source: tech-spec.md#FR-004]
   - Original fhirapp.py had `[:10]` chunk slicing hardcoded [Source: CLAUDE.md#architecture - mentions fixed 10-chunk limit issue]
   - This script must handle any bundle size: 5 resources or 500 resources
   - Limit applied ONLY where pedagogically necessary (e.g., "recent 10-20 Observations" to avoid overwhelming LLM with hundreds of lab results)
   - Grouping and extraction loops should iterate all resources without arbitrary cutoffs

8. **Contrast with Exercise 2's Naive Approach** [Inference]
   - Exercise 2 demonstrated that raw JSON is too large and unstructured for LLM
   - Exercise 3 solves this via grouping (semantic organization) and extraction (compact clinical fields)
   - Students see the technique working: grouped, extracted data fits context window and produces coherent summary
   - This motivates the "structured data preparation" pattern used throughout the AI+FHIR series

9. **Tiktoken Token Counting (Optional Enhancement)** [Source: tech-spec.md#FR-004, tech-spec.md#technology-stack]
   - Consider printing token count of the final extracted features string (before sending to LLM) so students see the size reduction from Exercise 2
   - Example: "Extracted features: 2,347 tokens (vs. original bundle: ~12,000 tokens)"
   - Reinforces the value of structured extraction
   - Use tiktoken with cl100k_base as approximation (same caveat as Exercise 2)

**Dependencies:**
- Story 1.3 (fhir_client.py) — for `get_everything_for_patient()`
- Story 1.2 (config.py) — for LLM client factory and model config
- Story 2.2 (exercise2-fhir-explore) — students should understand bundle size problem first (pedagogical dependency, not code dependency)

**Edge Cases:**
- Patient with minimal data (only Patient resource, no Conditions/Observations): summary should say "None recorded" for empty sections
- Patient with extensive data (100+ Observations): extraction limits (recent N) prevent overwhelming LLM
- LLM timeout or failure: catch exception, print "LLM request failed: {error}", do not crash
- Empty bundle: print "No data for patient {id}" and exit

**Testing Strategy:**
- Manual verification: Run with patient "2" → should print progress messages and final summary
- Manual verification: Run with patient having minimal data (find ID from 100Set/) → should handle gracefully
- Manual verification: Run with patient having extensive data → should limit and summarize without error
- Code inspection: Verify no Textual imports (`from textual` should not appear)
- Code inspection: Verify structured prompt includes "do not invent" instruction
- Code inspection: Verify no hardcoded `[:10]` or similar chunk limits in grouping/extraction loops

**Performance Note:**
- LLM call may take 10-60 seconds depending on hardware and model size [Source: tech-spec.md#performance]
- Print progress messages so students know script is working, not hung
